## 3. Design

### 3.1 Types (`src/types/`)

```ts
// events.ts
export type ServerEvent =
  | { type: 'RELAY_STATE';  nodeId: string; channel: number; data: { state: 'ON'|'OFF'; source: 'mqtt'|'button'|'boot' }; ts: number }
  | { type: 'SENSOR_STATE'; nodeId: string; channel?: number; data: { temperature: number; humidity: number }; ts: number }
  | { type: 'NODE_STATUS';  nodeId: string; data: { online: boolean }; ts: number }

// api.ts (assumed backend DTOs â€” flag to server plan for alignment)
```

### 3.2 `useNodesStore` (stores/nodes.ts) â€” including the pending/timeout state machine

```ts
state: {
  nodes: Map<string, NodeInfo>        // keyed by nodeId (use reactive Map or Record)
  loading: boolean
  loadError: string | null
}
// NON-reactive module-scope (timer ids must not live in reactive state):
const pending = new Map<string, { desired:'ON'|'OFF'; prevState:'ON'|'OFF'|'UNKNOWN'; timer: number }>()
// key = `${nodeId}:${channel}`; the reactive "pending" flag lives on the RelayChannel
// (add `pending: boolean` to the store's relay objects)

getters: {
  nodesByRoom: () => Array<[roomSlug: string, NodeInfo[]]>   // grouped, sorted by roomLabel
  nodeById: (id) => NodeInfo | undefined
}

actions: {
  fetchNodes()                       // GET /nodes, replace map (also called after every WS reconnect â€” resync)
  sendRelayCommand(nodeId, ch, desired)
  applyEvent(ev: ServerEvent)        // single dispatch entry point, called by useWebSocket
}
```

**Pending/timeout state machine â€” the 5s timer lives in the STORE, not the component.** Justification:
1. The event that resolves PENDING (`RELAY_STATE`) arrives in the store's `applyEvent`, not in any component â€” resolving where the signal lands avoids componentâ†”store callback plumbing.
2. The user can navigate Dashboard â†’ NodeDetail while a command is in flight; a component-owned timer dies on unmount and the toggle would hang or leak.
3. The same relay is rendered in two places (dashboard card and detail page); one store-owned pending flag keeps them consistent.
4. Testable headlessly (no mounted component needed).
`RelaySwitch.vue` stays dumb: props in, `toggle` event out.

Transitions for key `nodeId:ch`:

```
IDLE â”€â”€user toggle (allowed only if node.online && realtime.connected && !pending)â”€â”€â–¶ PENDING
  â€¢ sendRelayCommand: relay.pending = true; pending.set(key, {desired, prevState, timer: setTimeout(onTimeout, 5000)})
  â€¢ POST /command; if the POST itself rejects (network/5xx): clearTimeout, pending=false, toast error   â†’ IDLE
PENDING â”€â”€RELAY_STATE for (nodeId, ch)â”€â”€â–¶ IDLE
  â€¢ clearTimeout; relay.state = event.data.state (source of truth â€” even if it differs from `desired`,
    e.g. a physical-button race); relay.pending = false
PENDING â”€â”€5s timeoutâ”€â”€â–¶ IDLE
  â€¢ relay.state = prevState (visual revert); relay.pending = false
  â€¢ toast.add({ title: 'Device not responding', color: 'error', icon: 'i-lucide-wifi-off' })
PENDING â”€â”€NODE_STATUS offline for nodeIdâ”€â”€â–¶ IDLE (abort early, same revert + toast)
```

Notes: switch is `disabled` while PENDING (no queueing/double-fire); the switch visually stays at `prevState` with a spinner while pending (roadmap: only flips on the real event â€” no optimistic flip).

**Event â†’ store mutations (`applyEvent`):**
- `RELAY_STATE`: resolve pending as above; else just set `relay.state`/`source`. Unknown `nodeId` â†’ trigger `fetchNodes()` (covers a node that self-discovered after page load â€” Phase 1 simplicity).
- `SENSOR_STATE`: `node.sensor = { ...data, ts: ev.ts }` (drives SensorCard + live chart append via watcher).
- `NODE_STATUS`: `node.online = data.online`; if now offline, abort that node's pending commands (fail fast). Offline does not wipe relay states (retained state topics restore on reconnect anyway).

### 3.4 `useWebSocket` (composables/useWebSocket.ts)

Called once from `App.vue` setup. Uses stompjs's built-in reconnect (v7.1+) rather than a hand-rolled loop:

```ts
const client = new Client({
  webSocketFactory: () => new SockJS(`${location.origin}/ws`),  // factory (not brokerURL): SockJS objects are single-use per attempt
  reconnectDelay: 1000,
  maxReconnectDelay: 30000,
  reconnectTimeMode: ReconnectTimeMode.EXPONENTIAL,             // 1s,2s,4sâ€¦30s cap
  heartbeatIncoming: 10000, heartbeatOutgoing: 10000,
  onConnect: () => {
    realtime.setConnected()
    nodesStore.fetchNodes()          // RESYNC: refetch full state after every (re)connect â€” events missed while down
    client.subscribe('/topic/events', f => nodesStore.applyEvent(JSON.parse(f.body)))
  },
  onWebSocketClose: () => realtime.setReconnecting(),           // + increment attempts
  onStompError: frame => console.error(frame.headers.message),
})
client.activate()
```

Mock mode: the composable checks `import.meta.env.VITE_MOCK === '1'` and, instead of STOMP, subscribes to `mockSocket`'s emitter (same `applyEvent` path â€” stores are identical in both modes). Exposes `disconnect()` for tests. If stompjs happens to be <7.1, fallback is documented inline: `reconnectDelay: 0` + manual `setTimeout(activate, Math.min(1000 * 2**attempts, 30000))` in `onWebSocketClose`.

## 7. Gotchas

- **Nuxt UI v4 standalone**: (a) must wrap the root in `<UApp>` or `useToast`/tooltips silently do nothing; (b) the vite plugin generates `auto-imports.d.ts`/`components.d.ts` **only after the dev server or build runs once** â€” add both to `tsconfig.app.json` `include` and gitignore them; until the first run, the IDE will red-squiggle `UButton`/`useToast`; (c) `tsconfig.node.json` needs `"paths": {"#build/ui": ["./node_modules/.nuxt-ui/ui"]}` or vite.config.ts type-checking fails; (d) Tailwind **v4**: no `tailwind.config.js`, theme lives in CSS â€” don't paste v3-era config from tutorials; keep classes in templates (not concatenated TS strings) so the scanner sees them; (e) v4 semantic color props (`color="error"`), not v3 palette names.
- **sockjs-client in Vite**: throws `global is not defined` at import time â€” fix with `define: { global: 'window' }` (done in Â§4). Also pass an absolute URL (`${location.origin}/ws`); sockjs is picky about relative URLs. And with stompjs, always use `webSocketFactory` (never a cached instance): a SockJS object is single-use, one per reconnect attempt.
- **STOMP heartbeats**: client 10s/10s only works if the Spring side configures a heartbeat `TaskScheduler` on the simple broker (`setHeartbeatValue`) â€” flag this as a cross-cutting requirement to the server plan; with `0,0` from the server, dead connections are detected only by TCP timeouts, making reconnect sluggish.
